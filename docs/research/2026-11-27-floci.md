# Floci as the local AWS: findings

Verified by running Floci 2.5.0 locally on 27 November 2026 unless marked "docs".

## Conventions
- Image `floci/floci:2.5.0` (MIT). One port, 4566, for every service. Health: `GET /_floci/health`; the image has `/usr/local/bin/healthcheck.sh`.
- Endpoint `http://<host>:4566`, default region `us-east-1`, any non-empty credentials.
- A 12-digit access key id is taken as the account id; anything else is account `000000000000`. Resources are isolated per account and per region.
- State is in memory: a fresh container is a clean slate. It starts in about 2 seconds.
- ECS tasks and the ECR registry run as sibling Docker containers named `floci-aws-*`, through a mounted `/var/run/docker.sock`. They are not removed when Floci stops; remove them between runs.
- This machine already runs another Floci on host port 4566. Do not publish 4566; use host port 4577 or no host port.

## What works
- STS `GetCallerIdentity`, `AssumeRole` (the role must exist in IAM in the target account; assumed credentials resolve to that account).
- ECR: create a repository, then `docker push` to `localhost:<port>/<account>/<region>/<repo>:<tag>`. `DescribeRepositories`, `DescribeImages` with digests.
- ECS: `RegisterTaskDefinition` with tags, `ListTaskDefinitions` by family, `DescribeTaskDefinition` with tags, `TagResource`, `ListTagsForResource`, `CreateService`, `UpdateService`, `DescribeServices` (deployments, events), `DescribeTasks` with `stoppedReason`, `stopCode` and container exit codes. A healthy rollout goes `IN_PROGRESS` to `COMPLETED` in 3 to 10 seconds. Services need the pre-created subnet (`ec2 describe-subnets`, for example `subnet-default-us-east-1-c`).
- S3: put, get, copy, head, versioning with a `VersionId` per put, `ListObjectsV2`, `ListObjectVersions`. ETag is the MD5.
- KMS: `Encrypt`, `Decrypt`, `GenerateDataKey`. CloudWatch `PutMetricData`.

## Where it differs from AWS, and what to do
| Difference | Consequence for Yumdrake |
|---|---|
| `rolloutState` never becomes `FAILED`; a crashing container makes it flap between `IN_PROGRESS` and `COMPLETED`; an unpullable image stays `IN_PROGRESS` | Test the failed-rollout path with a stub ECS client in unit tests and with a response-rewriting proxy in front of Floci in end-to-end tests. `ecs-deploy` must also treat "the intended revision's tasks keep stopping" (from `DescribeTasks`) and its own timeout as failure, which is correct on real AWS too |
| Only "has reached a steady state" events | Do not assert on deployment event text in Floci tests |
| `DescribeImages` returns one entry per tag instead of one entry with all tags of a digest | Group image details by digest ourselves |
| Re-tagging with `PutImage` changes the digest | Set up test images with `docker push` of the same local image under several tags |
| `HeadObject` returns no SHA-256 checksum | Never rely on S3-reported checksums: compute SHA-256 from the bytes we read or wrote |
| `ExternalId` on a role's trust policy is not enforced | The external-id mismatch path is a unit test with a stub |
| Docs: `pendingCount` is always 0 and there is no second draining deployment | Do not assert on those |

Docs only, untested: `FLOCI_SERVICES_ECS_MOCK=true` skips Docker and reports tasks running; `FLOCI_STORAGE_MODE` for persistence; `FLOCI_HOSTNAME` when other containers call it.

## Compose block
```yaml
  floci:
    image: floci/floci:2.5.0
    ports: ["4577:4566"]
    volumes: ["/var/run/docker.sock:/var/run/docker.sock"]
    environment:
      FLOCI_HOSTNAME: floci
    healthcheck:
      test: ["CMD", "/usr/local/bin/healthcheck.sh"]
      interval: 3s
      timeout: 3s
      retries: 10
```
